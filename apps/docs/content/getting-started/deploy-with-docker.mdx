Parcelis ships published container images for the application and documentation site. The simplest way to run the platform is to use Docker directly when you already have PostgreSQL and S3-compatible storage services available.

## Requirements

To run Parcelis with Docker, the minimum requirements are simply those required to install and run Docker. The production Compose stack includes nginx as the proxy for the web app, API, and documentation site.

## Setting up Parcelis

Once Docker is installed, the rest of the process is straightforward. Start the web app container with the required environment variables:

```bash
docker run -d --name parcelis-app \
  -p 3000:3000 \
  -e DATABASE_URL=postgresql://parcelis:parcelis@postgres:5432/parcelis?schema=public \
  -e WEB_ORIGIN=https://parcelis.example.com \
  -e AUTH_COOKIE_DOMAIN=parcelis.example.com \
  -e AUTH_COOKIE_SECURE=true \
  -e EMAIL_FROM='Parcelis <no-reply@example.com>' \
  -e SMTP_HOST=smtp.example.com \
  -e SMTP_PORT=465 \
  -e SMTP_SECURE=true \
  -e SMTP_USER=your-smtp-user \
  -e SMTP_PASSWORD=your-smtp-password \
  -e S3_ENDPOINT=https://s3.example.com \
  -e S3_PUBLIC_ENDPOINT=https://s3.example.com \
  -e S3_BUCKET=parcelis-images \
  -e S3_ACCESS_KEY_ID=your-access-key \
  -e S3_SECRET_ACCESS_KEY=your-secret-key \
  parcelis/app:v0.4.1
```

The published documentation image is designed to be mounted at `/docs/` by the nginx proxy. Use the production Compose stack when serving the application and documentation site together.

```bash
docker compose --env-file .env.production up -d
```

:::caution
If you are planning to run Parcelis in a production environment, update the values for the database, object storage, and authentication settings before you expose the service publicly. Use strong, unique credentials and keep them out of shell history and version control.
:::

## Required environment variables

The app container expects the following values at minimum:

- `DATABASE_URL`: PostgreSQL connection string
- `WEB_ORIGIN`: the public origin used by the web app
- `AUTH_COOKIE_DOMAIN`: the cookie domain for authentication sessions
- `AUTH_COOKIE_SECURE`: set to `true` when the app is served over HTTPS
- `EMAIL_FROM`: sender address for transactional email
- `SMTP_HOST`, `SMTP_PORT`, and `SMTP_SECURE`: SMTP server connection settings; `SMTP_SECURE` must be `true` or `false`
- `SMTP_USER` and `SMTP_PASSWORD`: SMTP authentication credentials
- `EMAIL_SETTINGS_ENCRYPTION_KEY`: base64-encoded 32-byte key used to encrypt saved organization SMTP passwords
- `S3_ENDPOINT` and `S3_PUBLIC_ENDPOINT`: S3-compatible endpoint URLs
- `S3_BUCKET`: the object-storage bucket used for uploaded images
- `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY`: credentials for object storage

The nginx proxy exposes the web app at `/`, documentation at `/docs/`, and
the API at `/api/v1`.

## Optional environment variables

- `SESSION_IDLE_TIMEOUT_ENABLED`: defaults to `true`; set to `false` to disable the 15-minute inactivity timeout

For the complete `.env` reference, including TLS and STARTTLS guidance, see [Email configuration](./email-configuration). Organization administrators can configure SMTP in Settings → Organization → Email. Those settings take precedence for email sent to a user whose default organization has a saved configuration. The environment SMTP values remain the fallback.

### Feature flags

Feature flags control which optional features are available. Unset flags default to disabled; only the exact value `true` enables them.

| Variable                            | Default | Description                                                                                                                          |
| ----------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `FEATURE_FLAG_APPLICATIONS_ENABLED` | `false` | Enables application navigation, pages, templates, sent requests, status management, application notes, and role permission controls. |

To enable applications, add this to `.env` for local development or `.env.production` for Docker Compose:

```dotenv
FEATURE_FLAG_APPLICATIONS_ENABLED="true"
```

Provide the same value to both the web app and API. Restart local processes or recreate containers after changing it. When disabled, application pages and API operations are unavailable, including for administrators. Existing application data and role permissions are preserved.

For Docker Compose, `app-service.environment` in `docker-compose.yml` must include the mapping below. The repository's Compose file includes it; add it if using an older or custom file. An entry in `.env.production` alone does not pass the variable into the container.

```yaml
services:
  app-service:
    environment:
      FEATURE_FLAG_APPLICATIONS_ENABLED: ${FEATURE_FLAG_APPLICATIONS_ENABLED:-false}
```

For local development, `docker-compose-dev.yml` runs supporting services only. The web app and API run on the host; `pnpm dev` loads the root `.env` and passes its values to those processes. Set the flag in `.env` and restart `pnpm dev`; no flag mapping is needed in the dev Compose file.

Apply the changed environment with `docker compose --env-file .env.production up -d --force-recreate app-service`. For `docker run`, pass `-e FEATURE_FLAG_APPLICATIONS_ENABLED=true`.

When applications are disabled, `auth.me` and `roles.list` keep the permission matrix's resource keys but report all application and application-note actions as `false`. Role permission updates ignore those resources until the feature is enabled, preserving their stored permissions.
